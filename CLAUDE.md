# CLAUDE.md — ubx-schema-azure

## What this is

The real, published schema snapshot for the Azure provider — a frozen,
versioned `manifest.json` + `members/*.json` group, generated by
`ubx-provider-dynamic --generate-snapshot-group` from Azure's own real,
per-service ARM Swagger specs, committed here (not release-only) so a
reviewer sees the real diff. A `[providers.azure]` pin in `ubx` resolves
against this repo's own real GitHub Releases via `provider.AcquireSchema`.
Coordinating repo: `github.com/ubiquex/ubiquex`.

604 real members — 302 distinct Azure Resource Manager resource providers,
each fetched once and built into both a resource-mode and a data-source-mode
member from that one fetch.

## Session protocol

1. Read `STATE.md` first — current state only, rewritten not appended.
2. `STATE.md` is rewritten, not appended, as the LAST act of every session.
   Anything that becomes history moves to `HISTORY.md`.
3. Only reference Linear issue IDs given in the handoff prompt; never infer
   one.

## Repo-specific mechanics

- `.github/workflows/hash-watch.yml` — weekly cron + manual dispatch. Builds
  `ubx-provider-dynamic` from ITS OWN real, latest published release tag (not
  `main` HEAD — an untagged build stamps every regenerated snapshot with the
  meaningless `min_binary_version: "dev"`, UBI-194). Never auto-merges. With
  604 members, expect this to run long and touch many `members/*.json` files
  per real regeneration — only real, changed members are ever touched.
- `.github/workflows/publish.yml` — manual dispatch only, refuses to
  republish an existing tag. Verify a real release via `gh api
  repos/Ubiquex/ubx-schema-azure/releases/tags/v<version>` after dispatch,
  not the workflow's own exit status.
- Azure's own real specs split across shared files by relative path
  (`../../../../../../common-types/...`) — `ubx-provider-dynamic`'s own
  `internal/openapi.Bundle` rewrites every one of those into a real, local,
  network-free component before a snapshot is ever frozen (Azure's own ref
  graph is genuinely cyclic, not just deep, confirmed live — UBI-193). This
  repo is the first real group in this org published only after that fix
  landed; generation would have refused outright before it existed.
- A pinned resolution of this provider is real, but SLOW at first launch —
  ~54-56s wall time to the first RPC response, zero network, root-caused to
  the `GetProviderSchema` gRPC call itself, not parsing/translation/merging
  (UBI-195, filed, not yet fixed). Not this repo's own bug to fix, but worth
  knowing before assuming a hang.
